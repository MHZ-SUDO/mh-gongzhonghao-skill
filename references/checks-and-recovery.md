# 发表检查与异常恢复

## 提交前检查

每一项都根据本次现状核对。不要为了脚本通过而把未知项填true。review仅是助手审查证据，不是用户新增确认，也不能覆盖已有操作记录。

| 项目 | 视频 | 图文 |
|---|---|---|
| 授权 | 用户本次要求发布这一期视频 | 用户本次要求发布这一期配套文章 |
| 身份 | 当前账号、标题、video类型、草稿ID | 当前账号、标题、article类型、草稿ID |
| 素材 | 最终MP4、时长、片头中尾、音画、封面 | 最终DOCX、章节图序、公式、正文封面、视频组件如要求 |
| 校验 | 上传转码可用、标题已校对、无表单错误 | 标题独立填完、封面错误清除、公式图片加载、无溢出 |
| 设置 | 群发OFF、定时OFF、合集、原创、同步身份 | 群发OFF、定时OFF、合集、原创作者、赞赏与来源 |
| 预览 | 播放器与裁剪正确、已保存 | 读者页面/窄屏检查、首尾完整、已保存 |
| 防重 | 记录里无同一份已发/发表中，state未attempted | 同名视频不能当图文重复，图文本身无已发/发表中 |
| 点击 | 当前可见确认层、唯一目标、快照新鲜 | 同左，不能点后台其他草稿的发表 |

本期review JSON的结构如下（`reviewed_at`填实际UTC时间，取当前时钟，不复制示例；脚本要求10分钟内）：

```json
{
  "account": "本期配置中的公众号名称",
  "title": "第04期_本期真实主题",
  "scope_verified": true,
  "preview_verified": true,
  "media_verified": true,
  "settings_verified": true,
  "existing_record_checked": true,
  "reviewed_at": "2026-10-30T12:30:00Z",
  "editor_kind": "video",
  "editor_identity": "本次实际草稿或编辑器ID，不含token",
  "evidence_files": ["本期目录中的终稿预览和发表弹窗截图路径"],
  "notes": "逐项核对的发现，写实际账号、时长、封面和开关状态"
}
```

article-review的editor_kind为article。review时间过期或终稿变化应重做review；已经commit的任务不能因review变化再次提交。脚本在commit前重核本地素材SHA，但不能自动证明浏览器里的稿件就是该文件，也不能代替人机界面上的逐项检查。

## 接管已有线上记录，禁止伪造新提交

若本期视频由用户手动或前一会话发出，新建的本地state尚无该kind的attempt，可以用adopt登记已有线上状态。先核对类型、完整标题、封面、时长/正文特征和平台身份，证据格式如下：

```json
{
  "account": "本期配置中的公众号名称",
  "title": "第04期_本期真实主题",
  "kind": "video",
  "status": "pending",
  "platform_identity": "当前实际视频素材或发表记录ID，不含token",
  "existing_record_checked": true,
  "observed_at": "2026-10-30T12:30:00Z",
  "notes": "当次实际核对的类型、时长、封面、状态及截图路径；由既有线上记录承接，本次未提交"
}
```

状态仅pending或published，observed_at为过去10分钟内真实UTC时间。执行：

```powershell
& '<python>' -X utf8 '<skill>\scripts\publish_workflow.py' adopt --state '<本期>\state.json' --kind video --evidence '<本期>\existing-video.json'
```

adopt是本地只读观察登记，不需要发表授权，不操作平台；不会伪造本次attempt，仍会锁住该kind后续review/commit。另一kind独立处理。后续查询的真实回执用record更新。已commit的本次任务不再adopt，不用它改写原尝试历史；原state缺失时，先找回原记录和网页证据，不能把“文件不在眼前”当从未提交。

## 更新未提交内容与当次授权

已经有本期state时，不直接改冻结manifest，也不另建state来绕过记录。以下场景使用 `refresh`：原来只存草稿、现在用户明确要求发表；只发视频/图文的当次范围变化；尚未提交的MP4或DOCX验收后修订。

1. 先读原state与线上原稿。视频或图文已经attempted/adopt时，按原身份查询该类型；网页状态不明时不自动重发，用户知悉风险后明确要求重试的例外见异常表。
2. 修订本期config，填当前实际终版路径、当次授权原文、`mode`和`requested_action`。同一个state保持账号与期次；已有提交时，标题、合集、全局设置及共享封面内容也保持原值。只更新尚未提交的素材。
3. 使用**从未存在的新预检目录**；命令保留同一个state，保存旧清单及 `previous-state.json`，保留全部attempt/adopt/回执，清除未提交类型的旧review：

```powershell
& '<python>' -X utf8 '<skill>\scripts\publish_workflow.py' refresh --state '<本期>\state.json' --config '<本期>\config.json' --out '<本期>\preflight-v2'
& '<python>' -X utf8 '<skill>\scripts\publish_workflow.py' status --state '<本期>\state.json'
```

4. 未提交部分重新核对实际网页、预览、保存，再 `review → commit`。旧review不能继承。只发视频时，保留的旧article记录不获得提交权限；新增类型须在当次授权范围内，单独准备与核验。

已提交视频本地文件后来移走或被改写时，refresh仍保留**旧提交的哈希快照**，不采纳新字节、不解锁该视频；这不会阻塞未提交图文。每次commit只复验该类型及共享封面。已提交类型的原路径不能换成另一份素材；共享封面内容不得因修改图文而换版。

refresh不点击网页，也不证明当前用户授权。若命令超时，先读同一个state及新预检目录，确定是否已更新，不盲目重复、不删旧记录。明确失败后另选新的预检版本目录。普通pending查询无需refresh，直接record真实后续回执。

## 准确点击的操作方法

1. 读取当前URL、标题、账号、可见弹窗和当前快照。
2. 确认当前处于预期阶段：上传页、视频编辑器、图文编辑器、发表确认、微信验证或回执。页面不符先观察，不能点击接近位置的按钮。
3. 目标要在预期容器内且可见、可用、精确名称匹配；优先`@e`。只有快照没有可交互引用时，才用evaluate只读查看DOM属性以生成当前CSS定位。不得硬编码旧class、nth-child序号、录屏坐标或“最后一个绿色按钮”。
4. 一个改变一次：点击→新快照→核对预期。多步骤保存/发表禁止并行发送。对确认层中的“继续发表”核对说明后再点，不把底层编辑器按钮重复点一遍。
5. 异步上传/发表的调用超时只表示工具没回，不表示服务器没收到。先查询本次稿件和发表记录，再决定后续。状态不明时保留页面和attempted状态，不能自动试发另一份。用户知悉状态不明及可能重复后明确要求重试的特殊处理见下方异常表；原始状态和证据始终保留。

## 三次扫码判定

| 当前现象 | 该做什么 | 不该做什么 |
|---|---|---|
| 公众号登录页二维码 | 展示第1处当前码，扫码后核对账号 | 扫周报码、使用录屏旧码 |
| 视频终稿发表后的“微信验证” | 展示第2处当前码，明确视频标题 | 误称视频号独立登录、再开一个发表任务 |
| 图文终稿发表后的“微信验证” | 展示第3处当前码，明确图文标题 | 用视频验证码替代图文验证 |
| “扫码成功，请在扫码的微信上按提示操作” | 保持页面，等待手机确认与回执 | 立即关闭、刷新或报告已发表 |
| 二维码过期且当前同一验证窗允许刷新 | 只刷新此验证码一次，说明同一提交验证过期 | 回编辑器重新点发表、清空state |
| 扫码后账号不符 | 停写，说明期望/实际账号并回到正确登录流程 | 在错误账号继续上传 |
| 平台多要一项验证 | 读实际目的并告知，不隐藏额外步骤 | 绕过验证、声称严格三次已保证 |

二维码可能授予登录或发表能力，只在本次用户聊天展示当前码，不上传到外部服务。展示当前码后，有异步问题工具时弹窗提示“请扫码并完成手机确认，完成后选已扫码”；必须读取实际页面确认结果，回复、弹窗消失和HTTP 200本身都不是发表回执。等待时不需反复问“确认发布吗”，因为本次明确发布指令已有授权。

## 异常恢复表

| 现象 | 恢复动作 | 停止条件 |
|---|---|---|
| 桥接运行但扩展未连 | 按kimi-webbridge operations检查连接，说明需要打开/连接扩展 | 无可用连接时保留本地准备成果，不能假装浏览器已操作 |
| 标题/账号/期次有多个合理候选 | 从源文件和当前项目继续核对，仍不能唯一确定时一次问清必要信息 | 不在歧义素材上触发保存并发表 |
| DOM出现两个“发表” | 读取当前弹窗/角色与容器，定位唯一的当前层按钮 | 不能唯一定位就不点，重新截图/快照 |
| 上传进度缓慢 | 查看进度/转码状态；每15–30秒读取一次，保留同一任务 | 不反复重新上传；明确失败后才处理文件或网络 |
| DOCX导入中 | 留在同一导入任务，读进度与编辑器正文 | 导入覆盖提醒未明确本稿身份时不确认 |
| 导入后缺图/公式或横向溢出 | 使用原图和原公式修复网页，再预览；保存源Word | 未修复就不发表，也不称Word本地通过等于网页通过 |
| 一键排版新页空白 | 确认articlestruct任务页，查看原稿仍已保存；等待当前任务 | 约3分钟仍无变化先读状态；约5分钟仍无可读结果，回已保存原稿人工排版或报告，不自动新开任务 |
| 排版结果属于别篇或丢内容 | 不应用，回原稿；按章节/图片/关键公式检查 | 无法恢复本稿则保留草稿与源文件，不继续发表 |
| “必须插入一张图片”等红字 | 重新进入对应封面/图片表单，确认选择与保存后消息清除 | 有实际校验错误不能照录屏强点发表 |
| 群发默认ON | 关闭后读取OFF，再继续非群发 | 用户未要求群发不得打开或消耗通知次数 |
| “未开启群发通知”提示 | 核对预期非群发，再继续同一发表 | 不为消除提示开启群发 |
| 尚未提交素材哈希与冻结值不同 | 重新验收终版，用refresh和新预检目录更新原state，重新预览/review | 已attempted/adopt类型不解锁、不换稿重发；共享封面内容保留 |
| commit已成功但点击未返回 | 只读查询编辑器、验证窗、发表记录；保留attempted | 不reset、不换run目录绕过、不自动再次发表 |
| 受理不明，用户知悉情况和可能重复后明确要求重试 | 再查发表记录、原稿身份与当前页面；未见已发表/发表中时，在本期记录中追加用户新指示、检查结果和额外尝试时间，对同一原稿执行一次并保存实际回执；原state仍保留，用record更新后续状态 | 不把普通发表授权或等待超时当重试指示；不新建稿件、重置state或伪称首次未提交。若已出现发表中/已发表，按现有记录处理而不重试 |
| 确知commit后没有点到按钮 | 保存事实与现场；审查唯一目标以及本次是否存在提交 | 脚本设计不提供解除锁；需真实页面明确未提交及用户新的重试指示才另立一次尝试，不以猜测恢复 |
| 发表记录“发表中”/审核中 | 记pending，持续只读查看；分别报告另一类型是否完成 | 不重发、不把等待当失败，不无限占用会话 |
| 明确失败/拒绝 | 记failed、原文原因、源稿与链接；修复可逆内容 | 重试可能重复发表时需用户明确新的重试指示；不要笼统再问原已授权的正常发表 |
| 自动生成贴图草稿 | 只记录平台附加结果 | 不去发布、删除或改动它 |

## 本地记录和交付状态

建议每期目录包含：config.json、preflight/manifest.json及检查报告、state.json、video-review.json、article-review.json、终稿/弹窗/回执截图、简短发布结果。目录中的截图可有私有管理信息，默认不外传；对外链接使用实际阅读页地址，移除后台会话参数。

- `draft/未提交`：本地准备或草稿完成，尚未触发终稿发表。
- `attempted`：已记准备触发/已触发一次，后续状态不确定也禁止自动再试。
- `pending`：平台已接收或显示处理中，还没有已发表证据。
- `published`：本期对应类型在发表记录中为已发表，保存证据和可用链接。
- `failed`：平台明确失败，保留原因；不自动解除防重保护。

如果仍在手机验证或请求是否受理尚未知，不把一条临时状态汇报当任务结束，也不调用close_session关验证页。平台已经明确受理pending且仅剩后台处理时，保存平台身份和证据，可按桥接技能清理本次会话；下一次只读查询原记录，不重新发表。

交付时优先说本次每种内容的实际状态。若平台一直pending，可以给出可复核记录并说明处理未完成；不能为结束任务把它写成published，也不能默默添加未来监控或自动重发任务。
